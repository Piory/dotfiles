# コミットメッセージ作成スキル

## このスキルを適用するトリガー
次の依頼が来たら、このスキルを必ず使う。
- 「コミットメッセージを考えて」
- 「差分を見てコミットメッセージを作って」
- 「それでコミットして」
- 「git add してコミットして」

## 基本方針
- 原則として、このスキル内の手順を親エージェント自身が実行する。
- ユーザーがサブエージェントへの委譲を明示的に依頼し、Codex で `commit_message_writer` が利用可能な場合のみ、コミットメッセージ作成とコミット実行を委譲する。単なるコミット依頼を委譲の許可とみなさない。
- `commit_message_writer` を新規起動する場合は、起動ツールに `fork_turns: "2"` を明示する。直近2ターンより前のコミット対象・除外条件・承認内容は依頼文に補う。起動ツールがこの引数に未対応なら、全履歴の継承で代用せず、制約を報告して代替方法を確認する。
- 必ず差分確認後にコミットメッセージを作る。
- メッセージは日本語で作成する。
- 形式は `絵文字 type: 説明` を基本とする。
- `type(scope):` 形式のスコープは使わない（例: `feat(nvim):` は禁止）。
- 「絵文字不要」の指示がある場合は絵文字なしにする。
- 変更が論理的に分けられる場合は、無理に 1 つへまとめず用途別に分割コミットする。
- 分割単位は、スキル更新、Codex 設定、Claude 設定、ツール設定など、変更の目的や対象が異なる境界を優先する。
- コミット実行時は依頼範囲内の未追跡ファイルも内容を確認して含める。秘密情報や生成物は無条件に追加しない。

## 必須手順
1. `git status -sb` で変更ファイル一覧を確認する。
2. `git diff` と `git diff --cached`（必要ならパスを指定）および未追跡ファイルの内容を確認する。差分の理解に必要な周辺コードだけを読む。
3. 差分を用途別に分類し、1 コミットにまとめるべきか分割すべきかを判断する。
4. 変更内容に合う `emoji` と `type` を選ぶ。
5. メッセージ作成のみの依頼なら案を提示して終了し、ステージやコミットは行わない。
6. 「コミットして」など実行まで明示された依頼なら、同じ操作の承認を再要求せず、分類した単位ごとに対象ファイルだけを `git add` する。対象や意図が不明な変更がある場合のみ確認する。
7. ステージ済み差分が予定した単位と一致することを確認して `git commit` を実行する。対象外の既存ステージを勝手に解除・同梱しない。混在して安全に分離できない場合は確認する。
8. 成功したコミットのハッシュ・メッセージと残りの変更を確認して報告する。失敗時は未完了として理由を示す。コミット依頼を push の許可とみなさない。

## 重要な制約
- コミットメッセージ作成依頼では、不要なファイル編集をしない。
- AI生成の免責文（Generated with ... など）をコミット本文に入れない。
- ユーザーから明示指定がない限り、コミットタイトルにスコープ（`(nvim)` など）を入れない。
- 不明点がある場合は推測で進めず確認する。

## 絵文字の目安
- `✨ feat`: 新機能
- `🐛 fix`: バグ修正
- `♻️ refactor`: リファクタ
- `📝 docs`: ドキュメント更新
- `🔧 chore`: 設定・雑務
- `⚡️ perf`: 性能改善
- `✅ test`: テスト追加・更新
- `🚑️ hotfix`: 緊急修正
- `🔥 remove`: 削除系

## 出力テンプレート
### メッセージ提案のみの場合
```text
<emoji> <type>: <変更内容を日本語で簡潔に>
```

### 分割提案が必要な場合
```text
1. <emoji> <type>: <変更A>
2. <emoji> <type>: <変更B>
```
