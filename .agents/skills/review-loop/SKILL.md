# Review Loop

## 適用範囲と役割

親エージェントがレビューの実行、指摘の判定、修正、検証、最終報告を担当する。レビューだけを別プロセスの `codex review` に任せ、`review-fixer` などのサブエージェントを自動起動しない。ユーザーが委譲を明示した場合だけ、許可された範囲を委譲できる。

コード変更を伴う実装後に使用する。アプリケーションの実装コードに直接影響しない文書・説明・エージェント向け指示だけの変更では、ユーザーから明示的なレビュー依頼がなければ省略する。設定やスクリプトは拡張子だけで除外せず、実行時の挙動への影響で判断する。

レビュー専用プロセスや、親がレビューを担当すると明示された修正担当はこのスキルを再実行しない。レビューのみを依頼された場合は、指摘を報告し、許可なく修正ループへ進まない。

## 1. 対象と前提を確認する

ユーザー要求、合意した仕様、受け入れ条件、関連する指示を確認する。実装開始時の Git 状態と照合し、今回の変更と既存変更を区別する。開始時の記録がなければ変更の帰属を推測せず、必要な点をユーザーへ確認する。

```bash
command -v codex
git status -sb
git diff --stat
git diff --cached --stat
codex review --help
```

差分の内容と未追跡ファイルも確認する。仕様逸脱や実装漏れを先に解消し、必要なテスト、型検査、lint、build を実施する。テストを作成・変更する場合は `単体テスト設計・実装` スキルを確認する。

## 2. 読み取り専用でレビューする

未コミットの実装は次でレビューする。

```bash
codex --sandbox read-only review --uncommitted
```

ステージ済み・未ステージ・未追跡の変更が対象になる。既存変更も含まれるため、各指摘と今回の作業との関係を後で確認する。対象を狭める目的で既存変更を stash、削除、巻き戻ししない。

ユーザーがブランチやコミットを対象に指定した場合は、対象に応じて次のいずれかを使う。比較先を推測して固定しない。

```bash
codex --sandbox read-only review --base <比較先ブランチ>
codex --sandbox read-only review --commit <対象SHA>
```

対象指定のオプション同士や独自プロンプトを併用せず、インストール済み CLI の制約に従う。コマンドの終了まで待ち、終了状態とレビュー本文の両方を確認する。途中出力、空の出力、認証・通信エラー、強制終了を「指摘なし」とみなさない。レビュー専用プロセスに修正や追加レビューの起動を任せない。

実行失敗時は原因を確認して、安全に再試行できる場合だけ1回再試行する。再度失敗したら未完了として報告する。

## 3. 指摘を事実確認する

レビュー出力をそのまま修正指示にしない。各指摘の対象コード、呼び出し元、テスト、仕様、差分を読み、成立する入力・状態・実行経路と影響を確認する。

| 判定 | 基準 | 対応 |
|---|---|---|
| 修正対象 | 今回の範囲に属するバグ、回帰、仕様逸脱、セキュリティ・性能・保守性の具体的な問題が成立する | 根拠と検証方法を整理して修正 |
| 対応不要 | 誤検知、防御済み、主観的提案、依頼範囲外の既存問題 | 修正せず理由を記録。範囲外の重大な問題はユーザーへ報告 |
| 判断待ち | 調査しても成立条件や必要な仕様判断を確定できない | 質問して回答を待つ。推測で修正しない |

各回の対象、実行結果、指摘、重大度、確認した根拠、判定、修正内容、検証結果を保持する。重大度が出力にない場合は捏造しない。過去に対応不要とした指摘でも、新しい根拠があれば再評価する。

## 4. 親エージェントが修正・検証する

確認できた問題だけを、合意した仕様を維持する最小限の変更で修正する。無関係なリファクタリングや機能追加はしない。仕様変更が必要ならユーザーへ確認する。

指摘の再現条件と修正後の期待結果をテストで確認する。コード変更の最後に `simplify` スキルを使用し、今回の変更範囲だけを挙動を変えずに整理する。その後、関連するテスト、型検査、lint、build を再実行する。未実行・失敗した検証は成功扱いにしない。

認知していない変更を検出した場合は停止し、意図的か確認する。勝手に戻さない。明示的な依頼がない限りコミット、push、PR/MR 作成を行わない。

## 5. 修正を含めて再レビューする

修正後は必ず手順2へ戻る。修正箇所だけでなく、当初の対象と修正の両方を含む差分をレビューする。

ブランチ対象は同じ比較先を維持する。コミット対象に未コミットの修正を加えた場合、`--commit` だけを再実行しても修正は含まれない。対象コミットと作業ツリー全体を含む比較先を確認して `--base` に切り替えるなど、対象を取りこぼさない方法を選ぶ。無関係な変更が混ざる場合は範囲を明示して判定する。適切な比較先を確定できなければ確認を求める。

| 状態 | 終了の扱い |
|---|---|
| 最新の差分のレビューが正常終了し、有効な未解決指摘が0件で、必要な検証も成功 | 完了 |
| 根拠を確認した対応不要の指摘のみ残る | 除外理由を報告して完了 |
| レビュー失敗、必要な検証の未実行・失敗、仕様判断待ち、修正不能 | 未完了として理由と残存事項を報告 |
| 同じ有効な指摘が2回連続し、修正しても前進しない | 無限反復を止め、原因と必要な判断を報告。完了とはしない |

有効な指摘が残る限り、回数だけを理由に完了扱いにしない。修正後の再レビューを省略しない。

## 6. 最終報告

実装・修正の要約、検証結果、レビュー回数、修正した指摘、対応不要とした理由、未解決事項を日本語で報告する。指摘の一覧には表を使い、事実と推測を区別する。停止した場合は「レビュー完了」と記載しない。
